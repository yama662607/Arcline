# 04. 開発およびOSS運営プラクティス

## 開発ワークフロー

1.  **リポジトリ戦略**: `nisargkolhe/arcify`を元にした**Fork**として開発を開始する。ただし、GitHubの制約により公開リポジトリのForkを直接プライベートにすることはできないため、**「Privateミラー」方式**を採用する。
    -   元リポジトリを`--bare`でクローンし、新しく作成したプライベートリポジトリに`--mirror`でプッシュする。
    -   これにより、履歴を保持しつつ非公開で開発を進めることが可能になる。
    -   公開する準備が整った段階で、リポジトリをPublicに切り替える。

2.  **ブランチ戦略**: `main`ブランチを保護し、機能開発やバグ修正はすべてフィーチャーブランチ（例: `feat/command-palette`）で行い、Pull Request（PR）経由でマージする。

3.  **コミット規約**: **Conventional Commits**に従う（例: `feat:`, `fix:`, `docs:`, `refactor:`）。これにより、コミット履歴の可読性が向上し、後述するリリースの自動化が可能になる。

## CI/CD (継続的インテグレーション/継続的デリバリー)

-   **ツール**: GitHub Actionsを利用する。
-   **CIワークフロー**: Pull Requestが作成・更新されるたびに、以下のジョブを自動実行する。
    1.  `lint`: ESLintとPrettierによるコードスタイルのチェック。
    2.  `typecheck`: TypeScriptの型チェック。
    3.  `test`: Vitestによるユニットテスト。
    4.  `build`: Viteによる本番ビルドが成功することを確認。
-   **CDワークフロー**: `main`ブランチにマージされた際、`semantic-release`を使い、以下のプロセスを自動化する。
    1.  コミットメッセージから次のバージョン番号（SemVer）を自動で判断。
    2.  `CHANGELOG.md`を自動生成。
    3.  GitHubのタグとリリースを作成。
    4.  ビルド成果物（`arcline-extension.zip`）をリリースに添付。

## ライセンス (GPL-3.0)

-   **ライセンスの継承**: 元プロジェクトであるArcifyが**GPL-3.0**ライセンスを採用しているため、本プロジェクトもGPL-3.0を継承する。MITライセンスなど、他のライセンスに変更することはできない。
-   **遵守事項**:
    1.  **ソースコードの公開**: 拡張機能を配布（例: Chromeウェブストアに公開）する場合、対応するソースコードを誰でも入手できる状態にしなければならない（GitHubで公開すればこの要件は満たされる）。
    2.  **改変の明示**: コードを改変した旨をファイルやドキュメントに明記する。
    3.  **法的告知の表示**: 拡張機能のUI内（例: 設定画面の「About」セクション）に、著作権表示、無保証であること、ライセンス条文へのリンクを明確に表示する。

## 公開リポジトリの運営 (Community Health)

コントリビューターが参加しやすく、健全なコミュニティを維持するために、以下のファイルを整備する。

-   `README.md`: プロジェクトの概要、機能、インストール方法、デモGIFなどを記載。
-   `CONTRIBUTING.md`: 開発環境のセットアップ方法、ブランチ戦略、PRの作成方法など、コントリビューションの手順を詳述。
-   `CODE_OF_CONDUCT.md`: プロジェクト参加者の行動規範を定める。
-   `SECURITY.md`: 脆弱性を発見した場合の報告手順と連絡先を明記する（公開Issueではなく、プライベートな連絡手段を指定）。
-   **Issue/PRテンプレート**: バグ報告や機能提案の際に必要な情報を漏れなく記述してもらうためのテンプレートを用意する。
