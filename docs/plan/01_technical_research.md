# 01. 技術調査

## 既存のArc風拡張機能

- **Arcify**: Arc風UIとスペース管理を提供。Chromeのタブグループとブックマークをベースにしている。
- **Workona**: ワークスペース単位でのタブ管理に特化。プロジェクト切り替えに強い。
- **Vertical Tabs / VertiTab**: 純粋な垂直タブ機能を提供。軽量なものから多機能なものまで様々。
- **Toby / Session Buddy**: タブをコレクションとして保存するタイプ。

## AIブラウザの調査

- **Atlas, Dia, Comet**: いずれも「Chromiumベース」と公表されているが、拡張機能APIの互換性、特に`chrome.sidePanel`や`chrome.tabGroups`といった新しいAPIのサポート状況はブラウザやバージョンによって異なる。
- **調査メモ**: Atlas ではコンテンツスクリプトのコンソールからは `chrome.sidePanel` が `undefined` だったが、拡張機能の Service Worker コンソールを確認するとフルセットの WebExtensions API が利用できた。**API の可否は必ず Service Worker か extension context で確認すること。**
- **課題**: すべてのChromium派生ブラウザで同じAPIが動作するとは限らない。API存在チェックを行い、未実装の場合は代替UI（ポップアップウィンドウやページ内フローティングUI）にフォールバックする設計を組み込む。

## 技術スタックの検討

### React vs. バニラJS

- **React**:
  - **利点**: 状態管理とUI更新が抽象化されており、複雑なUIでも宣言的に記述できる。Framer Motionなどのライブラリと組み合わせることで、高度なアニメーションを効率的に実装可能。
  - **欠点**: バンドルサイズが大きくなりがち。
- **バニラJS (素のJavaScript)**:
  - **利点**: 軽量で高速。ライブラリ依存がないため、バンドルサイズを最小限に抑えられる。
  - **欠点**: 状態とUIの同期を手動で管理する必要があり、アプリケーションが大規模になるとコードが複雑化しやすい。

### 結論

本プロジェクトでは**React**を採用する。コンポーネントベースの開発により保守性を高め、豊富なエコシステム（状態管理、アニメーションライブラリなど）を活用して、高品質なUIを効率的に構築するためである。

### 状態管理

- **Zustand**: 軽量でシンプルなAPIを持つ状態管理ライブラリ。ReactのContext APIのボイラープレートを削減しつつ、必要な部分だけを購読するセレクタ機能により、パフォーマンスの最適化が容易。
- **Redux Toolkit**: より大規模で厳格な状態管理が必要な場合に適しているが、本プロジェクトのスコープではZustandで十分と判断。併用は不要。
